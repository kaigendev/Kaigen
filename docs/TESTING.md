# Стратегия тестирования Kaigen

Этот документ задаёт обязательный подход к тестированию Kaigen. Цель — проверять не только конечный снимок интерфейса, но и первый кадр, переходные состояния, гонки, нагрузку, portable-поведение и отсутствие утечки приватных данных.

## 1. Основные правила

- Тестируется актуальный код из этого репозитория. Старые копии не используются как источник исправлений.
- Перед тестами фиксируется `git status`; чужие и пользовательские изменения не перезаписываются.
- Обычные тесты выполняются с отключённым Tor. Сетевой тест с Tor проводится только по прямому требованию пользователя.
- Реальные пользовательские профили не используются для smoke- и регрессионных тестов. Для UI-сценариев создаются отдельные disposable portable-каталоги и тестовые профили.
- Нельзя считать исправление подтверждённым только по конечному скриншоту, успешному PID или существованию ZIP.
- Исправление ошибки обязательно получает минимальный автоматический регрессионный тест на найденную причину, а не только на внешний симптом.
- При изменении требований одновременно обновляются тесты и нормативная документация.

## 2. Уровни проверки

### 2.1. Статическая проверка

Обязательна после любого изменения:

```powershell
git diff --check
```

Дополнительно проверяются:

- отсутствие случайных приватных файлов и секретов;
- отсутствие неиспользуемого legacy-кода, бесконечных таймеров и неочищенных обработчиков;
- отсутствие `dangerouslySetInnerHTML`, исполнения строк и небезопасной передачи удалённых данных в WebView;
- согласованность русских и английских строк интерфейса;
- кроссплатформенность путей и системных действий.

### 2.2. Frontend

Базовый набор:

```powershell
npm run test:chat-navigation
npm run build
```

`test:chat-navigation` обязан покрывать чистые функции принятия решений: пороги экранов, приоритет индикатора, пользовательский/автоматический скролл, длинные текстовые блоки, независимые файловые карточки и корректную смену якорей.

Frontend-сборка подтверждает типы и production-компоновку, но не заменяет runtime-проверку WebView.

### 2.3. Rust и нативная логика

```powershell
cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

При изменении нативного кода, профилей, сети, файлов, импорта, PQ или упаковки выполняется полный набор `cargo test` через `scripts/build-portable.ps1`.

Rust-тесты должны проверять как минимум:

- UTF-8-разбиение длинных сообщений без потерь;
- фильтрацию недоверенного текста, статусов и имён файлов;
- portable-пути и запрет выхода из `downloads`;
- профили, непрочитанные события и одновременную работу профилей;
- передачи, повторные имена файлов и сохранение состояний;
- PQ-фрагменты и согласованный handshake;
- отсутствие блокирующего DNS в цикле профиля.

### 2.4. Интеграционная проверка WebView

Для изменений чата создаются два независимых disposable portable-каталога с двумя тестовыми профилями, взаимно добавленными в контакты. Пользовательские экземпляры можно сначала осмотреть, если пользователь их явно подготовил, но дальнейшие разрушающие или повторяемые тесты проводятся на собственных копиях.

Проверяется реальный Tauri/WebView, а не HTML-макет и не браузерный preview.

### 2.5. Portable-сборка

Обычное новое задание завершается локальной Windows x64 сборкой:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-portable.ps1 -ArtifactsDir <каталог-в-../outputs>
```

Созданный source ZIP является техническим побочным результатом и не выдаётся пользователю при обычной тестовой сборке.

## 3. Матрица тестов поведения чата

### 3.1. Направление и тип

Каждый изменённый сценарий проверяется для:

- входящего и исходящего текста;
- входящего и исходящего изображения;
- входящего и исходящего обычного файла;
- скрытого настройками изображения;
- незавершённой, приостановленной, ошибочной и завершённой передачи;
- служебной PQ-карточки, если изменение затрагивает общий контейнер сообщений.

### 3.2. Размер и последовательность

- сообщение в одну строку;
- сообщение в две строки;
- короткое многострочное сообщение;
- одно максимально большое Tox-сообщение;
- 3, 6, 7 и 8 максимальных протокольных фрагментов;
- одно высокое изображение;
- два последовательных изображения;
- три и более последовательных изображений;
- последовательность `текст → изображение → файл → текст`;
- одинаковые изображения, чтобы выявлять ошибочное повторное использование ключа или якоря;
- быстрая серия до завершения декодирования предыдущего изображения.

### 3.3. Исходная позиция пользователя

- точный конец чата;
- менее полутора экранов от конца;
- от полутора до двух экранов;
- дальше двух экранов;
- активное колесо/жест/перетаскивание полосы;
- чтение длинного непрочитанного блока;
- открытый результат поиска;
- переключение контакта или профиля во время отложенной коррекции.

Дополнительно сценарии повторяются при изменённом масштабе интерфейса, системном шрифте, узком/широком окне, изменении размера окна и, для Windows, при переносе между мониторами с разным DPI.

### 3.4. Что наблюдать

- первый кадр новой карточки: она сразу находится над composer;
- конечную позицию и сохранение контекста;
- отсутствие прыжка назад к старой карточке;
- отсутствие зависания ввода, прокрутки и окна;
- отсутствие полосы прокрутки при автоматическом скролле;
- правильную взаимную исключительность «Новые сообщения» и «В конец»;
- очистку непрочитанного только после фактической видимости;
- сохранение пользовательской позиции при чтении истории;
- устойчивость после декодирования изображения и каждого обновления прогресса.

## 4. Проверка первого кадра и гонок

Конечный скриншот недостаточен. Для ошибок «появилось снизу, затем поднялось» или «прыгнуло к старой карточке» используется один или несколько методов:

- покадровая запись/серия быстрых снимков нативного окна;
- инструмент управления Windows с захватом окна;
- временная диагностическая телеметрия в тестовой копии: ключ якоря, граница, `scrollTop`, `scrollHeight`, высота viewport, источник автоматического намерения;
- детерминированный unit-тест чистой функции выбора диапазона;
- контролируемая задержка декодирования большого изображения или частые обновления прогресса.

Диагностический код не должен попадать в финальную сборку, если он не является безопасной постоянной телеметрией. Если инструмент визуального контроля отказал, это явно фиксируется; автоматические проверки не выдаются за проведённый визуальный тест.

## 5. Тесты регрессий навигации

Минимальные обязательные утверждения:

- порог кнопки «В конец» строго больше 1,5 экрана;
- исходящее сообщение автоматически уходит вниз не дальше чем с двух экранов;
- непрочитанные имеют приоритет над кнопкой «В конец»;
- автоматический scroll-event не публикует навигационные элементы;
- короткое входящее позиционируется вниз до paint;
- длинный входящий диапазон сохраняет две строки исходящего контекста;
- пользовательский скролл блокирует автоматический перехват;
- 3/6/7/8 текстовых фрагментов образуют один диапазон;
- каждая карточка файла/изображения образует собственный диапазон без 900-мс текстовой задержки;
- третья карточка не наследует якорь второй;
- загрузка изображения корректирует только собственный актуальный диапазон;
- устаревший режим чтения завершается, когда диапазон перестал быть длинным;
- смена чата/профиля инвалидирует таймеры, кадры и намерения предыдущего экрана.

## 6. Производительность и отзывчивость

Для затронутой области оцениваются:

- отсутствие непрерывного роста CPU в покое;
- отсутствие повторного React-render при неизменном snapshot;
- ограниченное число `requestAnimationFrame` и таймеров на событие;
- прекращение поиска после закрытия;
- отсутствие синхронного чтения больших файлов в UI-потоке;
- прокрутка и ввод во время входящих пакетов и прогресса передачи;
- история с 20/50/100 сообщениями и полной загрузкой;
- отсутствие утечек обработчиков после многократной смены контакта и профиля.

Если интерфейс визуально «заклинил», проверяются CPU, `Responding`, активные таймеры/кадры, повторяющийся якорь и цикл `layout → scroll → state → layout`, а не только сетевой слой.

Для гонок дополнительно проверяются: закрытие приложения во время записи черновика/истории, offline-очередь, перезапуск во время передачи, быстрые пауза/продолжение/retry и устаревший snapshot после оптимистичного действия.

## 7. Безопасность WebView и файлов

Проверочные значения должны включать:

- `<script>alert(1)</script>`;
- HTML-теги и обработчики событий;
- кавычки, обратные кавычки и шаблонные строки;
- `javascript:` и похожие строки;
- управляющие байты и смешанный Unicode;
- такие же значения в нике, статусе и имени файла;
- имена с `../`, `..\\`, абсолютными путями и зарезервированными именами.

Ожидаемый результат: содержимое видно только как текст, код не исполняется, путь не выходит из portable-каталога, экспорт остаётся текстовым и приложение не блокируется.

## 8. Проверка portable-архива

После сборки архив распаковывается в новый чистый каталог. В проверочную распаковку до запуска записываются корректные настройки `data/tor-settings.json` с `enabled: false` без BOM. Затем проверяются:

- процесс продолжает работать и отвечает;
- `MainWindowHandle != 0`;
- загружены `toxcore.dll`, `pthreadVC3.dll` и модуль WebView (`EmbeddedBrowserWebView.dll`/WebView2);
- не появился новый Tor-процесс;
- запускается именно EXE из распакованного архива;
- архив содержит требуемые runtime-компоненты;
- архив не содержит `.tox`, истории, профилей, логов, кэшей WebView, пользовательских `downloads` и других приватных данных;
- вычислен SHA-256 уже окончательного ZIP.

Наличие PID без окна и WebView не является успешным smoke-тестом. Если тест случайно запустил Tor, процесс немедленно останавливается, причина устраняется и тест повторяется.

## 9. Кроссплатформенность

- Общая бизнес-логика и frontend-тесты должны проходить независимо от ОС.
- Windows проверяется настоящей Windows x64 portable-сборкой.
- Debian проверяется настоящим AppImage на Linux runner.
- macOS проверяется настоящими universal `Kaigen.app` и DMG на macOS runner.
- Нельзя имитировать другую ОС, переименовывать бинарники или считать frontend-сборку нативной проверкой.
- Системные действия «Показать в папке», буфер обмена, диалоги и portable-пути требуют платформенного теста.

## 10. Критерии завершения задачи

Обычная задача завершена, когда:

1. Требования перечитаны и сопоставлены с `docs/CHAT-BEHAVIOR.md`.
2. Найденная причина исправлена без нарушения соседних сценариев.
3. Добавлен регрессионный тест.
4. Пройдены релевантные frontend- и Rust-проверки.
5. Проведён требуемый runtime/визуальный тест либо честно зафиксировано ограничение инструмента.
6. Создана и проверена чистая Windows x64 portable-сборка без Tor и приватных данных.
7. Пользователю выдан один Windows ZIP и SHA-256.
8. Не выполнялись push, GitHub Actions, тег или Release без явной команды «сформировать релиз».

Полный релиз дополнительно требует нативных проверенных архивов Windows, Debian и macOS и единого source-архива из одного коммита согласно `AGENTS.md`.

## 11. Журналирование результатов

В итоговом сообщении указываются:

- исправленная причина, а не только симптом;
- добавленные регрессионные сценарии;
- фактически выполненные команды и количество прошедших тестов;
- был ли проведён визуальный тест;
- результат чистого smoke-теста и отсутствие Tor;
- путь к Windows ZIP и его SHA-256;
- отсутствие GitHub-публикации, если релиз не запрашивался.

В документации не закрепляются временные хэши, номера запусков и пути конкретных тестовых копий: они перепроверяются в каждой задаче.

Если дефект зависит от тайминга, полезно временно фиксировать последовательность событий монотонными метками времени и ключами сообщений. Логи не должны содержать текст сообщений, Tox ID, пути пользователя, ключи или содержимое файлов и удаляются из выдаваемой сборки.
