# Постоянные инструкции проекта Kaigen

## Источник истины и границы проекта

- Этот репозиторий является единственным актуальным исходником Kaigen для Windows, Debian и macOS.
- Поддерживай одну общую кодовую базу для всех платформ. Не создавай отдельные форки по ОС без прямого требования пользователя.
- Не возвращайся к старым копиям проекта, не начинай миграции и не добавляй legacy-код или обратную совместимость без прямого требования пользователя.
- Официальный репозиторий проекта: `https://github.com/kaigendev/Kaigen`.
- Не публикуй пользовательские профили, ключи, историю, журналы, кэши WebView или иные приватные данные.

## Неизменные продуктовые принципы

- Все разблокированные профили работают одновременно. Переключение активного профиля меняет только отображаемые данные.
- Tor, прокси, сетевой слой и компоновка окна общие для всех профилей. В одном экземпляре приложения используется только один общий Tor.
- Профильные данные хранятся единообразно в `profiles`, без параллельного legacy-хранилища.
- Тяжёлые операции должны выполняться асинхронно и не блокировать ввод, прокрутку или остальной интерфейс. При заметной длительности показывай понятный прогресс.
- Сохраняй portable-поведение: Windows хранит пользовательские данные рядом с EXE, Debian — рядом с AppImage, macOS — в `Kaigen-portable-data` рядом с `Kaigen.app`.
- Импорт обычного профиля и собственная история Kaigen работают кроссплатформенно. Комплектуемый импорт SQLCipher-истории qTox поддерживается только в Windows, пока пользователь прямо не потребует расширить его.
- При изменении интерфейса поддерживай русский и английский переводы в актуальном и согласованном состоянии.

## Правила разработки и проверки

- Нормативная логика чата зафиксирована в `docs/CHAT-BEHAVIOR.md`, а обязательный подход к проверкам — в `docs/TESTING.md`. Перед изменениями чата полностью прочитай оба файла и соблюдай их вместе с этим документом.
- Если задача меняет согласованное поведение чата или постоянный тестовый процесс, обнови соответствующий документ в той же задаче. Исправление регрессии чата без автоматического теста на найденную причину не считается завершённым.
- Перед изменениями проверяй состояние Git и сохраняй не относящиеся к задаче пользовательские изменения.
- После каждого блока задания перечитывай требования пользователя и проверяй, что все пункты реализованы, согласованы между собой и не создают тупиковых состояний.
- Выполняй релевантные тесты, frontend-сборку, Rust-форматирование и Rust-тесты соразмерно изменениям. Для релизных изменений выполняй полный набор проверок.
- Во время обычных тестов Tor должен быть отключён и не должен запускаться. Сетевой тест с Tor выполняй только по прямому требованию пользователя.
- Не запускай приложение на реальных пользовательских профилях для smoke-теста. Используй чистую распакованную portable-папку.
- Не считай сборку завершённой только по наличию ZIP: проверяй его состав, отсутствие приватных файлов, SHA-256 и, где возможно, запуск нативного приложения.
- В общении с пользователем называй результаты «архивами», а не «артефактами».

## Обычный цикл после нового задания: тестовая сборка

- Если пользователь дал очередное задание по исправлениям или интерфейсу и не запросил релиз, после завершения изменений и проверок создавай только локальную тестовую portable-сборку Windows x64.
- Для тестовой сборки не выполняй `git push`, не запускай GitHub Actions, не создавай тег или GitHub Release и не публикуй исходники либо Debian/macOS-сборки.
- Используй актуальный `scripts/build-portable.ps1`. Выходную Windows-сборку помещай в соседний каталог `../outputs` с понятным тестовым именем. Если сценарий дополнительно создаёт source ZIP, считай его техническим побочным результатом и не публикуй его как тестовую выдачу.
- Распакуй Windows ZIP в чистую временную папку, проверь состав и выполни короткий smoke-тест с отключённым Tor. Убедись, что новый процесс Tor не появился.
- В конце выдай пользователю один Windows ZIP и его SHA-256 для проверки изменений.

## Полный релиз — только по явной команде

- Полный релиз запускается только после явной команды пользователя «сформировать релиз» или однозначного эквивалента. Обычная просьба исправить код не разрешает публикацию.
- Команда на релиз разрешает завершить релизный цикл без повторных подтверждений: проверить изменения, подготовить версию и описание, сформировать целевой коммит, отправить его в официальный GitHub-репозиторий, дождаться нативных сборок, опубликовать релиз и исходники.
- Перед отправкой проверь полный набор тестов, сборок и состояние репозитория. В релиз включай только изменения текущего задания и явно согласованные сопутствующие изменения.
- Отправь точный релизный коммит в GitHub. Нативные Windows, Debian и macOS сборки получай через GitHub Actions из этого же коммита.
- Не имитируй сборки другой ОС и не переименовывай чужие бинарники. Требуются настоящие нативные архивы:
  1. portable Windows x64;
  2. Debian x64 с настоящим AppImage;
  3. macOS universal с настоящими `Kaigen.app` и DMG;
  4. единый архив исходников из того же коммита с подробными инструкциями для Windows, Debian и macOS.
- Скачай результаты GitHub Actions, проверь содержимое каждого архива, нативный формат файлов, отсутствие приватных данных и SHA-256. Ошибку CI нужно исправить; заменять отсутствующую сборку заглушкой нельзя.
- Создай GitHub Release с тегом и понятным описанием изменений, прикрепи все четыре проверенных архива. Опубликованные исходники, тег, release и архивы должны соответствовать одному коммиту.
- Скопируй финальные четыре архива в `../outputs`, затем выдай их пользователю в чат вместе с SHA-256 и ссылкой на GitHub Release.

## Долговечность инструкций

- Если новая явная инструкция пользователя конфликтует с этим файлом, выполняй новую инструкцию и затем актуализируй `AGENTS.md`, если изменение должно стать постоянным.
- Временные номера версий, хэши и состояние конкретного workflow не закрепляй здесь: проверяй их заново при каждом релизе.
