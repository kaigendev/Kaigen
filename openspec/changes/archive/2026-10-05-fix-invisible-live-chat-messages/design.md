# Design

## Context

См. `proposal.md`. В `src/App.tsx` история состоит из ограниченного серверного окна, DOM-окна и отступов. Существующая ветка обновляет фиксированный диапазон до live tail при нахождении рядом с концом; она зависит от предыдущего признака хвоста, геометрии и незавершённой навигации. Поэтому проверка только полученного snapshot или DOM недостаточна.

Исторический native-отчёт от 2026-10-01 содержал PASS для входящих с `firstVisibleUtc=null`: он подтверждал монтирование и сохранение якоря, но не видимую карточку. Текущая задача требует нового отрицательного контроля, устанавливающего оставшуюся причину.

## Goals / Non-Goals

**Goals:** восстановить согласованность данных, отображаемого диапазона и геометрии без изменения пользовательской семантики. Проверять реальный App, затем новый native artifact.

**Non-Goals:** переработка протокола, хранилища, темы, зависимостей и CI; публикация release и production.

## Decisions

1. Сначала воспроизвести дефект с синтетической историей на текущем App. Наблюдать снимок, карточку, видимую геометрию и восстановление после прокрутки раздельно. Скопированный renderer не даёт доказательства продукта.
2. Исправить минимальную установленную причину в текущем механизме окна или его синхронизации. Не использовать периодическое перемонтирование всего чата, искусственные scroll-события или расширение DOM до всей истории: они скрывают причину и нарушают якорь либо ограничение ресурсов.
3. Сохранить пользовательские и owner guards. Подгрузка данных не означает автоматическое включение следования концу; новые входящие и исходящие сохраняют разные правила позиционирования.
4. Расширить существующий runtime harness и при необходимости чистые функции окна. Проверка видимости обязана падать при отсутствующей ожидаемой карточке; ручное восстановление проводится только после зафиксированного отрицательного результата.
5. После frontend baseline и актуальных chat runtime проверок выполнить обычный Windows finish и отдельный локальный Web Lab finish с точными artifact identities. Исторический PASS не присваивается новому бинарнику.

## Risks / Trade-offs

- Исправление отображения может перехватить ручной якорь → тесты истории, поиска, длинного входящего, границ двух экранов и сообщений за время закрытия.
- Смена владельца во время запроса → задержанные ответы после смены чата/профиля и проверки отмены таймеров.
- Конечный DOM скрывает ошибку первого кадра → временные отметки и кадры до любых восстановительных действий; отдельная native проверка.
- Дополнительные запросы или renders при неизменном snapshot → контроль стабильного idle и ограниченности data/DOM окон.

## Migration Plan

Изменение не требует миграции пользовательских данных. Новый проверенный portable устанавливается штатной транзакцией только поверх программных файлов рабочего клиента, с сохранением `profiles`, `data`, `downloads` и явным relaunch. Исходные receipts и артефакты сохраняются; откат выполняется только отдельным разрешённым действием.
